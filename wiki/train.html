Механика обучения: оптимизаторы, LR-расписания, распределённый претрейн

Архитектура (см. предыдущие заметки серии) определяет, что вычисляет модель. Эта заметка — про то, как её вообще заставляют обучаться на кластере из тысяч GPU: чем обновлять веса, как менять learning rate по ходу, как не взорвать градиенты и как разложить модель, которая не помещается в память одной видеокарты.

Три формы LR-расписания
Learning rate (Y) на протяжении обучения (X) — все три начинаются одинаковым linear warmup, дальше расходятся
Cosine decay — плавно к нулю, самый распространённый WSD (warmup-stable-decay) — плато, потом резкий decay Constant после warmup — редко используется как есть

00Цикл обучения целиком

Всё, что ниже — детали одного и того же четырёхшагового цикла, повторяемого миллионы раз.

Один шаг обучения
1. forward: ŷ = model(x)  // вычислить предсказание — сюда относится вся архитектура из предыдущих заметок
2. loss: L = loss_fn(ŷ, y)  // обычно cross-entropy для CLM (см. заметку Transformer §05)
3. backward: ∇L = ∂L/∂θ  // backpropagation через весь граф вычислений
4. update: θ = optimizer_step(θ, ∇L, lr)  // §01–03 — как именно использовать градиент

Эта заметка — почти целиком про шаг 4 и вокруг него: чем обновлять параметры (§01–03), как менять lr по ходу (§04–05), как не дать градиентам взорваться или обнулиться численно (§06–07, §10), и как физически распределить эти четыре шага по тысячам GPU, когда модель и данные не помещаются на одну машину (§12–15).

01SGD и Momentum

legacy для LLMжив в CV/классике
SGD с Momentum
vt = β·vt-1 + ∇L(θt)  // накопленная «скорость», β обычно 0.9
θt+1 = θt − lr·vt

Momentum сглаживает шумные обновления и «проносит» оптимизацию через плоские участки/локальные неровности поверхности loss, накапливая скорость в стабильном направлении — механически похоже на физический шарик с инерцией, катящийся по ландшафту loss.

Почему не используется как основной оптимизатор для LLM: у SGD один общий learning rate на все параметры — для трансформеров с очень разными по масштабу градиентов частями (эмбеддинги vs глубокие слои) это плохо работает без тщательного per-layer тюнинга. Adam-семейство (§02) решает это адаптивно, параметр за параметром.
классические CV-сети (ResNet и др.)иногда для fine-tuning небольших моделей

02Adam / AdamW — стандарт по умолчанию

де-факто стандарт

Kingma & Ba, 2014 — адаптивный learning rate для каждого параметра отдельно, основанный на скользящих оценках первого и второго момента градиента.

Adam
mt = β₁mt-1 + (1−β₁)∇L  // момент 1-го порядка (среднее), β₁≈0.9
vt = β₂vt-1 + (1−β₂)∇L²  // момент 2-го порядка (дисперсия), β₂≈0.999
m̂t = mt/(1−β₁ᵗ),   v̂t = vt/(1−β₂ᵗ)  // bias correction — критично на первых шагах
θt+1 = θt − lr·m̂t/(√v̂t+ε)

Деление на √v̂ — это и есть адаптивность: параметры с исторически большим градиентом получают эффективно меньший шаг, с маленьким — больший. Bias correction нужен потому, что m и v инициализируются нулями — без коррекции первые шаги были бы искусственно занижены.

AdamW (Loshchilov & Hutter, 2017) — ключевая поправка
θt+1 = θt − lr·(m̂t/(√v̂t+ε) + λθt)  // weight decay применяется напрямую к θ, а не смешивается внутрь градиента

В исходном Adam L2-регуляризация добавлялась к градиенту перед адаптивным делением на √v̂ — из-за этого эффективная сила regularization для каждого параметра искажалась той же адаптивной нормировкой. AdamW «decouple» — применяет weight decay отдельно, напрямую к весам. Разница небольшая по формуле, но заметная по факту: AdamW стал стандартом для трансформеров именно из-за этого.

Занимаемая Adam/AdamW память — не мелочь: на каждый параметр модели хранятся ещё два (m и v) в fp32 — итого оптимизатор занимает 8 байт на параметр дополнительно к самим весам. Для модели в десятки миллиардов параметров это соизмеримо с памятью самой модели — прямая причина, почему ZeRO (§13) в первую очередь шардит именно optimizer state.
AdamW: GPT-3/4, LLaMA, почти весь совр. LLM-претрейн

03Новое поколение: Lion, Sophia, Muon

emerging

Lion (Google, 2023)

  • Найден автоматическим поиском по программам оптимизации (аналогично тому, как был найден Swish в MLP §05)
  • Использует только знак момента для обновления (sign(mt)), не сам градиент — экономит память (не нужен второй момент v), но требует более осторожного подбора lr и weight decay

Sophia (2023)

  • Использует приближение к диагонали гессиана (кривизне loss), а не только градиент — теоретически быстрее сходится за счёт учёта второй производной
  • Дороже вычислительно на шаг, но заявлен меньший общий compute до целевого loss

Muon (2024)

  • Ортогонализует обновление весов через приближённый Newton-Schulz на матрице градиента (не покомпонентно, как Adam, а с учётом структуры всей весовой матрицы)
  • Показывает выигрыш по compute-эффективности конкретно на матричных весах (линейные слои) — комбинируется с AdamW для эмбеддингов/норм, где неприменим

Общий тренд

  • Все три ищут способ использовать больше информации о геометрии loss (знак/кривизна/структура матрицы), чем чистый Adam, либо меньше памяти при сравнимом качестве
Статус на сегодня: ни один не вытеснил AdamW как безопасный дефолт для претрейна LLM с нуля — у каждого есть отчёты о заметном ускорении в конкретных сетапах, но AdamW остаётся выбором с наибольшим объёмом проверенной практики на масштабе. Разумная стратегия — AdamW, если не проводился отдельный эксперимент, подтверждающий выигрыш альтернативы именно на вашей архитектуре и масштабе.

04LR-schedules: зачем менять learning rate по ходу

mainstream

Warmup (общий для всех схем)

  • Первые несколько сотен–тысяч шагов lr линейно растёт от ~0 до целевого максимума
  • Причина: в начале обучения оценки m,v в Adam (§02) ещё не накопили статистику — большой lr на этом этапе легко «взрывает» обучение

Cosine decay (после warmup)

  • lr плавно убывает по косинусоиде до близкого к нулю значения к концу обучения
  • Самая распространённая схема — простая, не требует дополнительных гиперпараметров кроме общей длины расписания
WSD (Warmup-Stable-Decay) — более новый (2024) подход: после warmup lr держится константным долгое плато, и только в последние ~10-20% шагов быстро уходит в decay. Практическое преимущество перед cosine: длину общего обучения не нужно знать заранее (cosine требует зафиксировать общее число шагов для формы кривой) — можно продолжать обучение на плато сколько угодно, и запустить decay-фазу только когда решили остановиться.
Ключевая ошибка новичков: слишком короткий warmup или слишком высокий пиковый lr на большой модели — типичный симптом на кривой loss — резкий скачок вверх («loss spike») вскоре после начала обучения или после выхода из warmup.

05Batch size и масштабирование LR

Больший batch size даёт менее шумную оценку градиента — что позволяет (и обычно требует) пропорционально больший learning rate, чтобы использовать эту стабильность, а не тратить её впустую на маленьких шагах.

Linear Scaling Rule (Goyal et al., 2017)
lr_new = lr_base · (batch_size_new / batch_size_base)
Правило работает только до определённого порога — critical batch size: за ним увеличение batch size уже не даёт пропорционального ускорения сходимости (градиент и так достаточно точен, лишние примеры в батче не добавляют полезной информации) — просто тратит compute на больший батч без выигрыша по числу нужных шагов. Приблизительная оценка critical batch size для конкретной модели — предмет отдельных scaling-экспериментов (та же линия исследований, что Kaplan/Chinchilla scaling laws из заметки Transformer §08, но по batch size, а не по размеру модели).

06Gradient clipping

Global norm clipping
если ‖∇L‖ > max_norm:   ∇L ← ∇L · (max_norm / ‖∇L‖)  // масштабируем весь градиент целиком, сохраняя направление

Считается норма градиента по всем параметрам сразу (не по отдельности) — если она превышает порог (типично 1.0), весь вектор градиента пропорционально сжимается. Это защита от редких, но разрушительных «выбросов» градиента — например, из-за одного аномального батча или численной нестабильности на конкретном шаге.

Clipping — не средство против систематической нестабильности (слишком высокий lr, плохая инициализация) — это защита от редких выбросов. Если clipping срабатывает почти на каждом шаге — это симптом более глубокой проблемы конфигурации (lr, инициализация, precision), а не то, что нужно лечить более агрессивным clipping.

07Mixed precision: fp32 / fp16 / bf16 / fp8

bf16 — стандарт для LLM
ФорматБиты (знак/экспонента/мантисса)ДиапазонТочность
fp321/8/23большойвысокая
fp161/5/10узкий — легко overflow/underflowсредняя
bf161/8/7как у fp32 (та же экспонента)ниже fp16 по мантиссе, но диапазон не проблема
fp8варианты 1/4/3 или 1/5/2узкийнизкая, нужна аккуратная калибровка

bf16 победил fp16 для обучения LLM именно из-за экспоненты: та же ширина, что у fp32, значит тот же динамический диапазон — градиенты в LLM могут быть очень маленькими или большими, и fp16 с его узким диапазоном экспоненты регулярно уходил в overflow/underflow без дополнительных костылей.

При fp16 (в отличие от bf16) почти обязателен loss scaling: домножить loss на большую константу перед backward (чтобы маленькие градиенты не занулились в узком диапазоне fp16), и разделить обратно перед шагом оптимизатора. С bf16 эта техника, как правило, не нужна — ещё один довод в пользу bf16 как более простого дефолта.
fp8 (H100 и новее) — следующий шаг экономии, но требует per-tensor или per-block масштабирования и куда более аккуратной инженерии, чтобы не терять качество — пока не такой безусловный дефолт, как bf16, скорее продвинутая оптимизация для больших прогонов.

08Gradient accumulation

Если целевой batch size не помещается в память GPU за один forward/backward — можно накопить градиенты за несколько маленьких «микро-батчей» перед тем, как сделать шаг оптимизатора.

Gradient accumulation
for i in range(accumulation_steps):
  loss = model(micro_batch[i]) / accumulation_steps  // делим заранее, чтобы сумма градиентов = среднему по полному батчу
  loss.backward()  // градиенты складываются в .grad, не обнуляются между итерациями
optimizer.step()  // один раз, после накопления всех микро-батчей
Математически эквивалентно одному честному большому батчу (с точностью до деталей типа batch normalization, которая в LLM-претрейне почти не используется — см. заметку Transformer §07 про RMSNorm) — цена лишь в том, что шаг оптимизатора происходит реже по времени, при том же суммарном объёме обработанных данных.

09Регуляризация: что живо в LLM-претрейне, а что нет

ТехникаСтатус в совр. LLM-претрейнеПочему
Dropoutпочти не используютпри обучении на огромных, разнообразных корпусах в один эпох (или меньше) переобучение — не главная проблема; dropout скорее замедляет сходимость без пользы
Weight decayиспользуетсяработает больше как неявная регуляризация оптимизационной динамики (см. AdamW §02), чем как классическая защита от переобучения
Label smoothingредко для претрейнабольше актуально для классификации/классических seq2seq задач; для CLM на огромном словаре эффект менее выражен
Early stoppingне применимо в привычном видепри одно-эпоховом (или менее) обучении на веб-масштабных данных нет привычного «переобучения на train» в смысле классического ML
Общая причина сдвига: классические техники регуляризации разрабатывались в режиме «много эпох на ограниченном датасете» — типичный сетап LLM-претрейна (масштаб данных сравним или превышает число параметров, часто меньше одной эпохи) делает большинство из них менее релевантными, чем при обучении CNN на ImageNet.

10Трюки стабильности: z-loss, logit soft-capping, QK-norm

mainstream в совр. LLM

z-loss

  • Дополнительный член лосса, штрафующий log-sum-exp логитов за отклонение от нуля — не даёт логитам «уплывать» в очень большие значения, что стабилизирует softmax численно

Logit soft-capping

  • Применить tanh-подобное ограничение к логитам перед softmax (напр. в attention-скорах или на финальном выходном слое) — жёстко не даёт значениям выйти за диапазон, где начинаются численные проблемы

QK-norm

  • Применить нормализацию (RMSNorm) прямо к Q и K векторам перед вычислением attention-скора — не даёт скорам расти неограниченно с глубиной сети, известная причина нестабильности обучения на очень больших моделях

Общий мотив

  • Все три — реакция индустрии на конкретные, эмпирически найденные точки нестабильности при масштабировании LLM за пределы того, что было изучено на моделях 2018–2020 годов
Это те же общие принципы, что уже обсуждались для нормализации внутри блока в заметке Transformer (§07, §09) — здесь применены точечно к конкретным местам (логиты, Q/K), а не только к основному residual stream.

11Данные: curriculum, mixing, дедупликация

Curriculum learning

  • Порядок показа данных модели — не всегда случайный: некоторые рецепты сознательно откладывают самые сложные/специализированные данные (код, математика) на более позднюю стадию обучения

Data mixing

  • Пропорции разных источников данных (веб-текст, код, книги, диалоги) — явный гиперпараметр, который тюнят отдельно, а не берут «как есть» из сырого распределения корпуса
Дедупликация — недооценённая, но важная часть: почти дословные повторы в обучающем корпусе не просто бесполезны, а эмпирически связаны с эффектом memorization (модель запоминает конкретные строки вместо обобщения) и с нестабильностями loss на повторяющихся местах.

12Data Parallelism — базовый случай распределённого обучения

Простейшая форма: полная копия модели на каждом GPU, разные GPU обрабатывают разные микро-батчи данных, градиенты усредняются между всеми копиями перед шагом оптимизатора.

DDP (Distributed Data Parallel)
каждый GPU: ∇L_i = backward(model, micro_batch_i)
all-reduce: ∇L = mean(∇L₁, ..., ∇L_N)  // синхронизация градиентов между всеми N GPU
каждый GPU: θ = optimizer_step(θ, ∇L)  // идентичное обновление на всех копиях
Ограничение: каждый GPU должен вмещать полную модель + полный optimizer state (§02, 8 байт/параметр только для Adam) + активации. Для моделей от ~1B+ параметров это быстро упирается в память одной видеокарты — отсюда необходимость §13–14.

13ZeRO и FSDP: шардинг состояния оптимизатора

mainstream для крупных моделей

ZeRO (Rajbhandari et al., Microsoft, 2019) — вместо того чтобы дублировать optimizer state/градиенты/веса на каждом GPU целиком (как в чистом DDP), разбить их между GPU — каждый хранит только свою часть.

Относительная память на GPU по стадиям ZeRO
100% = обычный DDP без шардинга (условные величины, зависят от N GPU и размера модели)
СтадияЧто шардируется между GPU
ZeRO-1только optimizer state (m, v в Adam) — самая «тяжёлая» по памяти часть
ZeRO-2+ градиенты
ZeRO-3 / FSDP+ сами веса модели — каждый GPU в любой момент хранит лишь часть параметров, недостающие «подтягиваются» по сети непосредственно перед тем, как понадобятся в forward/backward

FSDP (Fully Sharded Data Parallel, PyTorch) — по сути открытая переиспользуемая реализация той же идеи, что ZeRO-3, ставшая стандартным инструментом в экосистеме PyTorch.

Цена ZeRO-3/FSDP — дополнительный сетевой трафик (постоянно подгружать/выгружать шарды весов) — при недостаточно быстрой межсерверной сети (interconnect) это может свести на нет выигрыш в памяти за счёт простоя GPU в ожидании данных.

14Tensor / Pipeline / 3D parallelism

ZeRO/FSDP (§13) шардируют состояние, но каждый GPU по-прежнему участвует в вычислении всей модели на своём микро-батче. Следующий уровень — разделить саму модель по вычислениям между GPU.

Tensor Parallelism

  • Разрезать отдельные матрицы весов (напр. внутри FFN или attention) между GPU — каждый считает часть одной и той же матричной операции, результаты собираются через collective-коммуникацию внутри слоя
  • Требует быстрой связи между GPU (обычно только внутри одной ноды, NVLink) — коммуникация происходит на каждом слое

Pipeline Parallelism

  • Разные GPU отвечают за разные диапазоны слоёв модели целиком — данные идут по конвейеру от одной группы GPU к следующей
  • Основная сложность — «pipeline bubble»: GPU для поздних слоёв простаивают, пока не придут первые микро-батчи от ранних — решается разбиением на много мелких микро-батчей (interleaved scheduling)
«3D parallelism» — одновременное применение всех трёх осей (data + tensor + pipeline) — стандартный подход для обучения моделей масштаба сотен миллиардов параметров на тысячах GPU: data parallelism между группами нод, pipeline — между группами внутри, tensor — внутри одной ноды с быстрым NVLink.

15Activation checkpointing

Уже упоминалось в заметке MLP (§10) применительно конкретно к FFN — здесь общий принцип. При обычном backward нужно хранить в памяти все промежуточные активации forward-прохода (они нужны для вычисления градиентов).

Checkpointing — обмен compute на память
forward: сохранить только активации на границах «checkpoint»-сегментов, не внутри них
backward: при необходимости — пересчитать недостающие активации внутри сегмента заново (второй forward), затем посчитать градиент
Цена — примерно на 30% больше compute (лишний частичный forward-проход), выигрыш — активации хранятся не для всей глубины сети, а только для чекпоинтов, что часто позволяет обучать модель, которая иначе физически не поместилась бы в память GPU при заданном batch size.

Почему конкретно отказались

Чистый SGD (без адаптивности) для LLM

  • Один общий lr плохо подходит для параметров с сильно разным масштабом градиента в трансформерах — Adam решает это адаптивно

fp16 без явных костылей

  • Узкий динамический диапазон экспоненты регулярно приводит к overflow/underflow градиентов — bf16 с более широкой экспонентой снял саму необходимость в loss scaling

Dropout и классическая регуляризация в претрейне

  • Спроектированы для режима «много эпох на ограниченных данных» — почти не применимы к однопроходному обучению на веб-масштабных корпусах

18Как это соотносится с NOVA TITAN

Заметка специально под текущий стек: v0.1-скелет, нестандартная архитектура (RWKV-state + linear attention + Titans-память), обучение вероятно не на кластере из тысяч GPU.

AdamW + warmup+cosine — безопасный старт для v0.1, а не место для экспериментов §02 §04

Учитывая, что сама архитектура уже нестандартна (собственные state/memory/fusion модули), разумно не комбинировать архитектурный риск с оптимизационным — AdamW и обычный warmup+cosine дают наибольший запас проверенной практики, чтобы проблемы обучения было проще отличить от проблем архитектуры.

QK-norm и z-loss стоит рассмотреть заранее, если стек включает нестандартный linear attention §10

Кастомные attention-реализации (в отличие от давно отлаженных библиотечных) статистически чаще подвержены именно тем проблемам — неограниченному росту логитов/скоров с глубиной, — для которых эти трюки и были придуманы. Дешевле заложить их сразу, чем диагностировать нестабильность обучения постфактум.

Gradient checkpointing — вероятно нужен раньше, чем распределённый параллелизм §14 §15

Для одиночной или небольшой multi-GPU конфигурации (в отличие от кластера в тысячи GPU) activation checkpointing — куда более сразу применимый инструмент, чем tensor/pipeline parallelism: даёт возможность обучать на большем контексте/батче на доступном железе без усложнения инфраструктуры распределённого обучения.
